# Compare layouts and make visual decisions

The owner requested a browser-first comparison: create three layouts from the answered brief, open them for review, and use visuals when a consequential choice needs feedback. Version 0.6.0 makes this part of the website workflow. It adds instructions and a generated-prompt update; it does not claim a fresh three-layout runtime trial of the existing SENSU example.

## Compare the right amount of work

For a new site or substantial visual redesign, start with one representative page and its primary interaction in three different layouts. Share the audience, business goal, truthful copy, main action and supplied brand constraints. A second representative surface is useful only when its task differs enough to need another decision. The full site is implemented once after selection.

The options should change information order, composition, hierarchy or navigation strategy. Three colors applied to the same arrangement do not make three layouts. All options deserve comparable content, completeness and care. An agreed cream/forest palette is compatible with several compositions; it is not a selected layout.

Preserve a specifically chosen layout, an approved design to implement faithfully, or a targeted repair. That exception should be a recorded project fact. It should not become a reason to skip comparison merely because a palette or a broad style was answered earlier.

## Show the actual options

Use one reachable local comparison with stable A/B/C names and direct option URLs, or separately reachable pages if that fits the host. Each option explains its audience/task fit in one sentence. Offer matched desktop and phone views so the user can compare without remembering tabs. A review picker belongs to the development preview rather than automatically becoming part of the customer's finished product.

Operate important controls before presentation. Primary links reach supported destinations, the main interaction responds, and pending/error/recovery states are visible where relevant. Identify simulated data and unconnected operations. Use the existing local preview tools; a visual review does not require a new framework, dependency or public deployment.

Verify the actual reachable address and preview ownership, then open the comparison in the user-facing browser. Respect a browser the user specified. Keep direct links and matched annotated screenshots available beside a short comparison table:

| Option | Structure and reading path | Why it may fit | Tradeoff | Evidence |
| --- | --- | --- | --- | --- |
| A — project-specific name | Actual content order and main action | Audience/task rationale | Concrete usability or maintenance cost | Working URL and labeled views |
| B — project-specific name | Actual structural difference from A | Audience/task rationale | Concrete usability or maintenance cost | Working URL and labeled views |
| C — project-specific name | Actual structural difference from A/B | Audience/task rationale | Concrete usability or maintenance cost | Working URL and labeled views |

This table is a presentation shape, not three predefined design styles. The agent derives the actual directions from the client's field, content and tasks. Still images support composition review; operate the page to review motion, navigation and feedback.

If no browser is available, report that operation as NOT_RUN. Share supported entry links, valid captures or clearly labeled wireframes. A remote container's localhost may require forwarding. A schematic or generated mockup must not be presented as an implemented page.

## Ask after the comparison is visible

Ask for a selection, a combination of named elements, a focused revision or rejection of all three. Explain the recommendation through the user's task and the visible tradeoffs. Keep it easy to answer, for example: choose A's reading order, B's first-screen composition, C's navigation, or describe a change.

When a preference is required, wait for it before expanding the dependent visual direction. Content verification, backend contracts and other independent authorized work may continue. Silence does not select an option. If the user explicitly delegates design selection, record the agent's reasoned decision, present its basis and continue within the existing development authority. Do not request development permission again merely because a visual comparison happened.

For a combination, reconcile the result into one coherent system, update the affected preview, and retain the precise selected elements. Preserve the option identities and feedback in the existing decision record. Update the UI/UX prompt and page/action/motion contracts before template expansion. Selection establishes a visual direction; acceptance still requires actual working flows and evidence.

## Use a focused visual packet for later decisions

Use a sitemap for menu grouping, a flow diagram with representative screens for entry/return paths, matched forms for single-step versus staged input, and the same records at desktop/phone widths for table versus list/detail decisions. Motion choices need a working sequence and interruption/reduced-motion alternatives. Roles and data visibility benefit from an actor-to-screen diagram with an explicit access rule.

Each packet contains the user's task, option IDs, visuals or entry links, meaningful differences, tradeoffs, recommendation and one precise question. Use text labels as well as color. Inspect ordinary technical facts directly rather than asking users to choose them. A diagram supports a decision; it does not prove feasibility, runtime behavior or external authorization.
