# Reporting problems and proposing work

Reproducible issue reports are welcome. Include the version, host/runtime, operating system, intended result, actual result, minimal non-sensitive steps, and relevant sanitized output. Identify whether the issue concerns skill decisions, documentation, the example, or a platform capability.

Use fictional data. Never attach passwords, API keys, cookies, CSRF tokens, session secrets, customer records, or a .local folder. Use [the security route](SECURITY.md) for sensitive findings.

This is a source-available no-modification project. Do not submit a modified fork, translation, patch, or derivative distribution without prior written permission. A problem description or proposed behavior is enough to start a discussion. Contact info@karmenloop.com for modification rights; acceptance of an issue is not a grant of those rights.

Authorized changes must preserve notices, match the workflow's evidence boundaries, and pass relevant checks. Reports, source review, browser operation, independent QA, and release acceptance remain separate facts. No roadmap, response time, or merge commitment is implied.

## Documentation and release changes

Keep the English and Simplified Chinese entry pages and guides aligned. Explain the reader’s actual task with project-specific examples. Use concrete English commit subjects. New ordinary filenames and versioned release assets use lowercase kebab-case without spaces; conventional README, LICENSE, SKILL and metadata names remain unchanged. Before release, compare each package, version label, command, and current image with the documented behavior. Label diagrams, synthetic data, historical evidence, and unverified integrations accurately.
