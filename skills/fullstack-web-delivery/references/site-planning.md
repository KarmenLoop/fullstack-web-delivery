# Complete project and website plan

The plan must be delivered before implementation. Delivery is not an extra approval gate when local development is already authorized.

# # Architecture

Assign responsibilities for public pages, client state, API boundary, business rules, authentication, administration, structured storage, files, external services, and operations. Explain which are processes versus modules in one application. Preserve a suitable stack; choose alternatives using content, task, runtime, maintenance, and handover needs.

# # Sitemap and page inventory

List primary and secondary navigation, detail ownership, footer, admin menu, and signed-in differences. For each route record audience, task, entry, sections, primary/secondary action, data source, role, SEO, API, and acceptance identifier. Count templates, actual content URLs, and state/language variants separately. Derive page count from content and tasks, not a universal quota.

Define desktop and phone menus, current state, expansion, Escape, focus, touch, detail orientation, and return paths. Preserve/redirect existing routes during a redesign.

# # Content and templates

Homepage order follows the user's decision: audience/problem -> relevant offering -> credible evidence -> next action. Use facts; clearly identify missing material.

Product templates share name, category, summary, audience, value, specifications, price/inquiry, conditions, proof, FAQ, and action. Service templates share problem, scope, exclusions, steps, outputs, timing basis, collaboration, pricing basis, evidence, FAQ, and consultation. Render each promised field; a planning paragraph is not implementation evidence. Use service-specific steps and outputs.

Include microcopy: labels, loading, empty, errors, receipts, controls, and recovery. Identify content maintenance, preview, publication, withdrawal, translations, and owners.

# # Form, admin, API, and data

For each form specify fields/constraints/required guidance, purpose, privacy, spam defenses, endpoint, record, staff entry, permitted roles, processing owner, states, receipt, duplicates, and failure recovery. State exactly where staff see the result. Notification is separate from saving.

Document method/path, caller, authentication, roles/resources, input/output, errors, idempotency, pagination, limits, writes, audit, and tests. For external APIs name official documentation, configuration, and sandbox/real state. Define entity relationships, ownership/tenants, retention, deletion, export, backup, and migration.

# # Business, delivery, and acceptance

Record public company facts, narrative evidence, claims, media permission, pricing, and applicable policies. Include transactions only where required. Map requirement -> user scenario -> component/API -> data/admin -> implementation -> verification/evidence.

Give recommended/alternative routes, milestones, dependencies, local preview, account strategy, reviewer responsibility, defects, production preparation, and rollback. Unknowns need an owner, blocked scope, and recovery condition. Use the repository's [full planning template](https://github.com/KarmenLoop/fullstack-web-delivery/blob/main/docs/project-plan.md) when available; this reference specifies the portable requirements.
