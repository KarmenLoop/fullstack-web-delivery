# Three layouts and visual decisions

Use this process for new websites, substantial visual redesigns, or a consequential visual choice. The complete plan and project-specific specifications still precede prototype code. Mark the initial layout decision pending; keep the known business, brand and engineering requirements concrete.

## Establish the comparison scope

Default to three layouts of the representative page and its primary interaction. Select the page by business value and design uncertainty; add a second representative surface only if a substantially different task, such as administration, needs its own decision. Build the rest of the site once after selection.

Reuse existing answers. An agreed palette, tone or industry is a constraint shared by the three options. A specifically chosen layout, supplied design to implement faithfully, or targeted repair is a reason to preserve that direction instead. Record the applicable reason without asking the same question again.

The three options must differ in information order, composition, hierarchy or navigation strategy. Each must plausibly serve the same audience and core task. Color, radius or stock-photo swaps alone are not different layouts. Do not pad the comparison with deliberately weak alternatives.

Use the same truthful copy, available media, core CTA and realistic data, at comparable completeness. Preserve each design's intended structure at phone width rather than mechanically shrinking desktop. Explain any deliberate content difference so the user can judge it fairly. References inform principles, not copied brand identities.

## Build, operate and open

1. Create one local review entry with stable A/B/C identities and separately reachable option URLs, or three directly comparable pages if the host supports that better. Give each option a descriptive name and one-sentence rationale.
2. Render the representative content and primary interaction. Every enabled control navigates to a supported destination or performs its declared action. Clearly identify simulated data and unconnected operations; keep real submissions out of a visual demonstration unless separately intended and authorized.
3. Operate each option before presentation: primary action, return path, keyboard focus and the important pending/error/recovery states. Inspect actual desktop and phone CSS widths, wrapping, readability and meaningful motion. Static captures alone do not establish interaction quality.
4. Verify the reachable address and owned preview process. Open the comparison in the user-facing browser, respecting a specified browser and the host's actual tools. Provide direct option links and matched screenshots so the user can compare without remembering three tabs.
5. Present the important differences before asking for feedback: reading order, proposition, primary action, navigation, content density, phone behavior and motion purpose. Label all views and annotate only the changes that affect the decision.

Use a concise comparison table next to the visuals. A recommendation may explain audience/task fit and implementation cost, while keeping all three options equally usable. Provide an easy way to select one, combine named elements, request a change or reject all three.

If browser access is unavailable, say which preview step is NOT_RUN. Provide reachable links, existing valid captures or labeled wireframes using available tools. A schematic is not a rendered page, a generated mockup is not a working interface, and a local address in a remote container may need supported forwarding. External publication retains its own authorization boundary.

## Gather a real decision

Ask a focused preference question after the concrete comparison is visible. For example: choose A's reading order, B's first-screen composition, C's navigation, or describe a different direction. Refer to stable IDs and visible elements rather than subjective adjectives alone. Ask for one consequential decision at a time when possible.

When feedback is required, retain the pending choice and continue independent work such as content verification, data contracts or backend work already authorized. Wait for the answer before committing the dependent visual direction. Silence and elapsed time are not selection. If the user explicitly delegated design selection, inspect the options, record the agent's reasoned choice as delegated rather than human approval, present its basis and continue. Development authorization alone does not establish a preferred layout.

For combinations, identify the chosen structure and specific imported elements, reconcile the result into one coherent system and show the affected preview. Keep the prior options available through the decision and retain a lightweight record afterward. New business requirements may change the plan; do not silently call that a cosmetic revision.

## Use visuals for consequential choices throughout development

Choose the smallest representation that resolves the question:

| Decision | Useful comparison |
| --- | --- |
| Page hierarchy, content density or first-screen composition | Matched working views and annotated screenshots |
| Navigation, section grouping or entry/return paths | Sitemap or labeled flow diagram with representative screens |
| Form length, single-step versus staged submission | Clickable flow with required fields, pending, error and receipt states |
| Table, record list or detail drawer | Same sample records and task at desktop and phone widths |
| Motion or linked state | Operable before/after sequence with interruption and reduced-motion alternatives |
| Roles or data visibility | Actor-to-screen/data diagram; written access rule remains authoritative |

Each decision packet states the user's task, option IDs, visuals/entry links, meaningful differences, tradeoffs, recommendation and the exact question. Ordinary technical facts are inspected directly. A wireframe does not establish technical feasibility, and a technical diagram does not establish commercial consent. Keep diagrams legible with text equivalents; color alone must not carry the distinction.

## Preserve the choice in the specification pack

Use the project's existing decision ledger rather than a second tracker. Retain the affected page/task, shared constraints, A/B/C descriptions and preview/capture references, actual checks, pending or selected state, feedback source, exact selected elements and next action. For selection use human, explicitly delegated agent, or pending; distinguish it from runtime acceptance.

Update the UI/UX implementation prompt, design/page/action/motion contracts and affected acceptance scenarios. Mark earlier plans provisional until the relevant choice is resolved. A selected layout is permission to follow that visual direction within existing scope, not proof of complete functionality or authorization to publish.
