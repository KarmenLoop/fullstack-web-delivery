# Acceptance, evidence, and recovery

Use the project's existing structure. A new project may keep PLAN.md, DESIGN-RESEARCH.md, pages.csv, interactions.csv, api-contracts.md, content-claims.csv, acceptance.csv, PROGRESS.md, DECISIONS.jsonl, and evidence/ under docs/web-delivery. Small projects can keep short tables in one plan rather than duplicate a ledger.

Record requirement, surface, environment/source revision, role/data, steps, expected/actual result, status, evidence, executor, time, and defect/dependency. Use PASS, FAIL, NOT_RUN, BLOCKED, or NOT_APPLICABLE, with the actual scope. Evidence must match the tested source; recheck affected behavior after changes.

Per-flow acceptance covers normal, failure, permission, data, recovery, keyboard, phone, and applicable motion. The final regression includes actual public routes/content, core end-to-end flows, production build, metadata/status, and agreed persistence. Match the same business identifier across receipt, API, storage, staff details, state, and audit. Separate save and external notification outcomes.

Keep actual command, working directory, exit code, and useful raw output. Save matching screenshots with measured CSS viewport and scale; record operated interactions separately. Pure visual edits do not need implementation-mirroring tests. Run meaningful existing checks and repeat beyond affected scope only when a real concern justifies it.

A screenshot, detector result, successful build, or author report is not complete acceptance. Author runtime verification, independent screenshot/source review, independent runtime QA, physical-device work, human design approval, and public deployment are separate claims. A scoped ship verdict must retain its checklist scope.

Deliver runnable source, a directory index, complete plan, real startup/configuration, preview/admin addresses, credential retrieval, APIs/data, content/media provenance, evidence, open defects, deployment conditions, and rollback. Source archives exclude runtime secrets/state. Validate archive CRC, manifest hashes, exact intended file membership, and exclusions. Retain earlier releases.

For interruption, record completed work, current source, process ownership, next dependency-ready task, failure evidence, and recovery condition. Resume by verifying actual state and authorization rather than trusting an old status label.
