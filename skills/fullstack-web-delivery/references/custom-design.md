# Client-specific design

## Build the design brief

Derive industry, segment, audience, primary tasks, decision concerns, real evidence, content scale, brand voice, constraints, and devices from existing material. Ask only for missing decisions. A delegated visual choice is not a reason to repeat a style interview.

## Research in order

1. Study two or three relevant mature businesses or products in the client's field. Explain relevance to their audience and task. Use a reliable basis before claiming an objective industry ranking.
2. Apply established principles, including Apple HIG where useful: hierarchy, grouping, alignment, progressive disclosure, feedback, and purposeful interruptible motion. A principle is not a mandate to give every brand the same materials or visual skin.
3. Find GitHub implementation candidates. Distinguish visual reference, copied code, and installed dependency. Verify the actual license, version, compatibility, and cost. Do not invent an official Apple Web UI package.

Record source URL, review date, observed pages/devices, relevant task, adopted principle, rejected feature, project translation, and license/dependency decision. If a page cannot be inspected, disclose that limit. Stop when the comparison supports the decision.

## Translate rather than combine skins

Define one coherent composition: content order, grid, container, type, spacing, color, density, imagery, components, states, breakpoints, and motion. Explain three to five decisions using the brief. Preserve one main component system and motion approach unless a concrete missing capability justifies another dependency.

Use a hero that explains the client's work, licensed real material, or clearly labeled original demonstrations. Without genuine cases, show process and capability rather than invented endorsements. Distinct services need distinct mechanisms, not three copies of a checklist with new icons.

Marketing explains value and trust; administration helps people find, judge, and process work. Share tokens, but choose density and actions by task. If a service template promises steps and deliverables, render the actual service-specific steps and outputs.

## Two representative-page checks

Visual: clear proposition and next step; intentional hierarchy, spacing, imagery, readable content, and phone line wrapping. Compare the adopted principles, not arbitrary imitation percentages.

Task: operate the primary flow. Phone users must discover status and action. A horizontally scrollable table with no page overflow may still hide its useful columns. Use priority columns or a dedicated record list when appropriate. Required-field guidance belongs before input.

Expand templates after both checks. Technical layout checks do not establish aesthetic quality. Without an independent reviewer, report self-review. Never convert silence into user approval. Review a concrete correction list, repair material issues, and stop unbounded polish loops.

## Interaction evidence

Check error-alert focus, success-heading focus, reset-to-first-field focus, sign-in failures, and return focus after exit completes. Temporary disabling, replacement, and unmounting can lose focus. Use pending markers for unreturned statistics, not false zeros.

Verify actual CSS viewport, page/local scroll width, content readiness, and screenshot scale. Requested tool dimensions are not evidence they took effect. Keep invalid early captures outside target-device pass claims. A bad probe payload is distinct from an application failure.

Preserve decisions, before/after images, failure/repair records, and review scope. Author runtime tests, independent screenshot/source review, independent runtime QA, and human design approval are separate results.
